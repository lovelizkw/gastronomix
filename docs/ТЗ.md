# Техническое задание на веб-приложение «Gastronomix»

> Редакция от 27.10.2026. Описывает фактически реализуемый объём функциональности.
> Исходный концептуальный документ проекта (с перспективными модулями: сканирование
> штрих-кодов, AI-распознавание продуктов) — см. `docs/attachments/Комиссаренко_ТЗ_Gastronomix.docx`.

## 1. Назначение и цели проекта

**Назначение.** «Gastronomix» — веб-приложение для учёта продуктов дома
(«цифровой холодильник»), просмотра каталога рецептов и ведения собственных
рецептов с расчётом КБЖУ.

**Цели:**
- организовать единую цифровую базу продуктов пользователя;
- предоставить каталог из 30 рецептов с пищевой ценностью (КБЖУ);
- позволить пользователю создавать, редактировать и удалять собственные рецепты
  (с фото, количеством ингредиентов и КБЖУ);
- автоматически предлагать рецепты, соответствующие продуктам из «Холодильника».

## 2. Роли пользователей

| Роль             | Описание                                                                  |
| ---------------- | ------------------------------------------------------------------------- |
| Гость            | Просматривает лендинг, может зарегистрироваться или войти                  |
| Пользователь     | Ведёт свой «Холодильник», видит каталог и свои рецепты, создаёт/правит/удаляет свои рецепты |
| Сервис (система) | Подбирает рецепты по продуктам пользователя, изолирует данные между пользователями |

## 3. Функциональные требования

### ФТ.01 Регистрация и авторизация
Пользователь создаёт учётную запись (имя, email, пароль) и входит в систему.
Пароли хранятся в виде хешей (better-auth), сессии — в БД. Все разделы
приложения, кроме лендинга и страниц входа, доступны только авторизованным
пользователям (клиентские «гейты» + серверная проверка в каждом API-вызове).

### ФТ.02 «Холодильник» — учёт продуктов
Пользователь добавляет продукты: название, категория, количество в свободной
форме («3 шт», «200 г»). Продукты можно удалять. Каждый пользователь видит
только свои продукты.

### ФТ.03 Каталог рецептов (30 блюд)
В базе данных хранится 30 рецептов каталога (общих для всех пользователей):
название, время приготовления, ингредиенты, способ приготовления, фото,
КБЖУ на порцию. Каталог наполняется идемпотентными SQL-миграциями
(`0003_seed_recipes.sql` — 18 блюд, `0004_seed_recipes_catalog.sql` — ещё 12).

### ФТ.04 Подбор рецептов по наличию продуктов
Список рецептов ранжируется по совпадению ингредиентов с продуктами из
«Холодильника» пользователя (алгоритм `matchRecipes`): чем больше совпадений,
тем выше блюдо в выдаче. Если совпадений нет, показываются все рецепты.

### ФТ.05 Создание собственного рецепта
Пользователь заполняет форму:
- название, время приготовления, число порций;
- **ингредиенты с количеством**: список пар «продукт + количество»
  (добавление/удаление строк, до 30 ингредиентов);
- **фото блюда**: файл JPEG/PNG/WebP, автоматически уменьшается до 1000 px
  и сжимается (JPEG q≈0.75) в браузере, сохраняется в БД как data-URL
  (ограничение ≈2,6 МБ); фото необязательно — подставляется картинка по умолчанию;
- способ приготовления (до 2000 символов);
- **КБЖУ на порцию**: калории (0–5000), белки/жиры/углеводы (0–500 г).

Сервер валидирует данные (zod) и сохраняет рецепт привязанным к автору.

### ФТ.06 Управление своими рецептами
Пользователь может отредактировать любой свой рецепт (та же форма с
предзаполнением) и удалить его (с подтверждением). Каталог изменять нельзя.
Чужие пользовательские рецепты недоступны ни на чтение, ни на запись:
все запросы фильтруются по `user_id` текущего пользователя на сервере.

## 4. Нефункциональные требования

- **Производительность:** отклик интерфейса на действия (добавление продукта,
  сохранение рецепта) — не более 1 с при штатной нагрузке; подбор рецептов
  выполняется на клиенте без обращения к серверу.
- **Безопасность:** передача данных по HTTPS; хеширование паролей; серверная
  аутентификация каждого вызова API (middleware); параметризованные SQL-запросы
  (защита от SQL-инъекций); валидация всех входных данных на сервере (zod),
  включая формат и размер загружаемого фото; изоляция данных per-user.
- **Надёжность:** миграции БД применяются транзакционно и идемпотентно;
  ошибки загрузки изображения обрабатываются с уведомлением пользователя;
  разрушающие действия требуют подтверждения.
- **Переносимость БД:** приложение работает и с облачным PostgreSQL (Neon),
  и со встроенной PGLite (локальная разработка) без изменения кода —
  источник схемы один (`migrations/*.sql`).
- **Совместимость:** актуальные версии современных браузеров (desktop/mobile),
  адаптивная вёрстка (Tailwind CSS).

## 6. Структура базы данных

Подробно — в `docs/db-schema.md`. Ключевые сущности:
`user`, `session`, `account`, `verification` (better-auth);
`products` (продукты пользователя);
`recipes` (каталог + пользовательские рецепты, в т.ч. `ingredients_json`,
`portions`, `image`, КБЖУ).

## 7. Пользовательские сценарии

1. **Регистрация и первый вход:** пользователь создаёт аккаунт, попадает
   в «Кухню»; разделы защищены — без входа выполняется редирект на sign-in.
2. **Наполнение холодильника:** пользователь добавляет продукты; лента
   рецептов перестраивается — сверху блюда, которые можно приготовить
   из имеющегося.
3. **Свой рецепт:** пользователь открывает вкладку «Свой рецепт», заполняет
   название, добавляет строки ингредиентов с количеством («курица — 400 г»),
   загружает фото, указывает КБЖУ и порции, сохраняет — карточка появляется
   в ленте с пометкой автора и доступна для правки/удаления.
4. **Правка рецепта:** в ленте пользователь нажимает «Изменить», форма
   открывается с текущими значениями; после сохранения карточка обновляется.

## 8. Критерии приёмки

- регистрация/вход работают; неавторизованный доступ к «Кухне» невозможен;
- в каталоге ровно 30 рецептов, у каждого — фото, время, ингредиенты, КБЖУ;
- продукты и рецепты изолированы между пользователями;
- свой рецепт создаётся с ингредиентами+количеством, порциями, фото и КБЖУ;
  фото сохраняется и отображается после перезагрузки;
- свой рецепт редактируется и удаляется (с подтверждением); чужие — нет;
- подбор по «Холодильнику» поднимает подходящие рецепты наверх;
- `tsc --noEmit` и `npm test` проходят без ошибок.

## 9. Ограничения и перспективы

Текущая версия не включает (зарезервировано в концептуальном ТЗ):
сканирование штрих-кодов, AI-распознавание продуктов по фото, планирование
меню, учёт сроков годности, мобильные приложения. Архитектура (server
functions + PostgreSQL) допускает добавление этих модулей без переработки
ядра.
